# rc.3 手动导出性能差异诊断

日期：2026-10-28。本文记录 rc.3 修复前的诊断和临时进程级补救试验。**后续已将修复加入 rc.4，见 [rc.4 验证记录](RC4_VALIDATION.md)**；原 rc.3 EXE 本身未被修改。

## 结论与边界

同一台 Windows 11 / i7-14650HX / RTX 4060 Laptop 电脑上，正常启动的 rc.3 导出速度明显低于测试环境。对同一实际应用实例的 FFmpeg 子进程显式请求 HighQoS 后，完整视频导出由 119.1 秒降到 37.7 秒，成品逐字节一致；恢复默认策略的反向短片段对照再次变慢。

证据指向 Windows 自动 QoS 性能调度是关键因素。GPU 解码和编码在快慢两种情况下均已启用，低 GPU 频率不能解释为“没用显卡”。CPU 调度影响供帧、继而使 GPU 等待是合理解释，但没有采集线程级调度轨迹，不能声称已确定 Windows 的具体分类触发条件。没有证明所有 Windows/显卡均有此问题。

微软文档说明，未显式控制 EXECUTION_SPEED 时，系统会自行推断 QoS；显式禁用该项 throttling 对应 HighQoS。查询到 ControlMask=0、StateMask=0 只表示系统管理，并不能排除自动调度影响。参见 [SetProcessInformation 官方文档](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-setprocessinformation)。

## 素材、设置及初始现象

- 原片：1249.733313 秒，1920×1080，约 30fps，8 位 yuv420p AV1，有 AAC 音频。
- 设置：整片、4 倍速、消音、较小 MP4、自动 NVIDIA 解码与编码。
- 成品：312.433333 秒，1280×720，30fps，H.264 + 静音 AAC，117,593,927 字节。
- 用户最初截图：141.4 秒；插电。手动重试日志：17:39:31.488 → 17:41:54.716，管线约 143.23 秒。
- 手动重试前有一轮未应用倍速，日志输出时长仍为 1249.733 秒；用户取消并应用参数后重新导出。那轮不计入对照，不能用它解释最初正确四倍速的慢速结果。

## 其他已完成的排查

- 源码管线整片：38.04 秒，其中片段渲染 37.43 秒、最终重新封装 0.20 秒，探测与编码器选择合计不足 1 秒。
- 原 rc.3 冻结副本、桌面同路径 EXE、通过 Shell 启动的隔离实例：分别约 38.2、37.6、37.7 秒，输出哈希相同。
- 源码与桌面包的 FFmpeg SHA256 相同：`2ce797a0f88d7f067180338fb227f7b1928ea727bd9a4d7a1d022f7c52af71a3`。
- 两分钟短片段的有/无控制台、`-nostdin`、stdin 重定向对照均约 4.2 秒，未单独复现差异；实际 AppData 缓存位置对照约 4.28 秒；隔离实例自动打开浏览器约 5.8 秒。
- 当前实际实例经 API 也可出现慢速，因此无需依赖浏览器自动点击来继续诊断。computer-use 在读取 Edge 时无法可靠确认 URL 而停止；没有完成浏览器界面自动化对照，也未绕过该检查。
- 诊断期间新 API 会话重复上传同名素材出现两次探测失败；同文件外部 ffprobe 正常，新文件名的相同内容副本可继续测试。该现象未定位，不能据此认定原片损坏；后续若调查上传问题应另行复现。

## 已验证的补救办法与后续实现建议

仅对本次导出的 FFmpeg 子进程调用 Windows `SetProcessInformation(ProcessPowerThrottling)`：读取原 flags，`ControlMask |= 1`、`StateMask &= ~1`，即显式关闭 EXECUTION_SPEED throttling。原 flags 为 0/0，测试仅修改确认为本次导出的子进程，进程结束后没有持久影响。没有更改全局电源计划、GPU 功率上限、核心亲和性或进程优先级类别。

当时的实现建议：在 `ffmpeg_util.run_ffmpeg()` 创建子进程后尽早应用这项策略；仅 Windows 尝试，API 不支持或权限不足时继续现有处理并记录诊断，不能因此令导出失败。保留取消和 CPU/NVIDIA 回退行为。上述方案已在 rc.4 实现，并补充异常回退和真实便携包验证；原 rc.3 EXE 仍需退出后升级。

原始证据：`build/rc3-diagnosis/final-summary.json`、各轮 `report.json`、`gpu.csv`、`policy.json`；手动采样在 `manual-telemetry/`。一次性测试脚本也在该目录，包含本机路径与实验选项，未作为生产工具发布。文件名重复导致的诊断脚本启动/收尾错误不计为产品验证失败；已有成功结果以保存的报告、输出哈希和实际应用日志为准。
